# إثبات إصدار الموقع الحالي

يولّد `python -m client_web.build_site --site <checkout>` ملف
`/client/release-manifest.json` من ملفات البناء الفعلية. يضم الالتزام الكامل
للمستودع، رقم البناء وتاريخه، مراجعة المحرك والقواعد، بصمة `engine.zip`،
وبصمة SHA-256 لكل ملف منشور تحت `/client/`. تبقى حزمة ZIP الخاصة بمحرك Python
هي `bundle_sha256`؛ أرشيف Sites الخارجي له بصمة تخزين منفصلة في سجل النسخة.

بعد دمج الشفرة وبناء الموقع من التزام `main` المدمج ودفع مصدر Site وحفظ نسخته
ونشرها **على المشروع الحالي فقط**، شغّل:

```bash
python ops/release/verify_live.py --strict-release --expected-commit "$(git rev-parse HEAD)" --output live-release-proof.json
```

الحالة `MATCH` تتطلب تطابق ملفات Python داخل الحزمة الحية مع المستودع، وتطابق
الالتزام مع كل من manifest و`client-source.json`، وتطابق بصمات جميع ملفات
العميل التي يعلنها manifest مع الملفات المنزلة من الموقع الحقيقي. أي اختلاف
يرجع رمز خروج غير صفري. هذه مطابقة نشر تقنية فقط، وليست اعتمادًا معماريًا أو
قانونيًا.

تشغيل `Live site engine provenance (informational)` مراقبة سابقة للنشر؛ لونه
الأخضر لا يمثل شهادة تطابق. بعد النشر شغّل `Live release gate` يدويًا على
`main`؛ هذا التشغيل حاجب ويفشل عند `MISMATCH`، ويرفع JSON دليل الفحص.

احتفظ بمعرّف نسخة Site السابقة ومعرّف نشرها قبل كل نشر. عند فشل النشر الجديد
استعمل أداة Sites لنشر النسخة السابقة المحفوظة على المشروع نفسه، ثم أعد فحص
الموقع؛ لا تستنتج نجاح الرجوع من أمر النشر وحده.
